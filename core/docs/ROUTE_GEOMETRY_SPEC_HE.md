# זאב כחול — מפרט גאומטריית נתיבים וסימולטור

מסמך זה הוא מקור האמת המחייב לגאומטריית הנתיבים ולתרחישי הסימולטור. אין לפתח צורת נתיב, topology, מעבר בין מקטעים או מודל שגיאה שלא מוגדרים כאן. אם פרט חסר או אינו חד-משמעי — עוצרים ושואלים לפני מימוש.

## 1. סדר עדיפויות בין מסמכים

1. מסמך זה קובע את גאומטריית הנתיבים ואת התנהגות הסימולטור.
2. `ADAPTIVE_ROUTE_LIFECYCLE_HE.md` קובע את lifecycle האדפטיבי של Candidate/Confirmed/Replacement.
3. `V1_SPEC_HE.md` נשאר מפרט המוצר הרחב; במקרה של סתירה בנושא גאומטריה או זמני זיהוי, שני המסמכים לעיל גוברים.

## 2. עקרונות כלליים

- כל נתיב מנוטר הוא מסלול סגור ומחזורי.
- קיימת הפרדה בין עקבה נצפית בפועל לבין נתיב אפקטיבי.
- עקבה יכולה לכלול רעש, drift, רוח, דגימות חסרות, בליטות, approach לפני הכניסה למסלול ו-exit לאחר היציאה ממנו.
- אין להניח שקווים הנראים ישרים במודל הם ישרים מתמטית בפועל; המסווג חייב לסבול עקמומיות רכה.
- אין לאשר topology לפי זמן קבוע. הזמן משמש רק כציר נתונים וכאומדן period; evidence גאומטרי הוא שקובע.
- Buffer היסטורי מקסימלי: 40 דקות. זהו חסם זיכרון בלבד, לא זמן המתנה.

## 3. משפחת SI

`SI` הוא נתיב סגור קומפקטי שבו יחס הציר הארוך לציר הקצר קטן או שווה ל-1.5.

צורות נתמכות:

- מעגל.
- מתומן.
- צורה חופשית סגורה אחרת, כל עוד היא קומפקטית ועומדת ביחס הצירים.

המסווג אינו רשאי להחליף SI באליפסה לצורך הייצוג האפקטיבי. הצורה האפקטיבית נשמרת כ-centerline קנוני של העקבה עצמה, עד 64 נקודות.

דוגמאות סכמטיות:

```text
Circle        Octagon       Free closed
   ○             ⯃           ╭────╮
                            ╭─╯    ╰╮
                            ╰──╮  ╭─╯
                               ╰──╯
```

## 4. Hippodrome יחיד

Hippodrome הוא מסלול SO דמוי capsule/racetrack: שני legs המחוברים בשני אזורי פנייה מעוגלים.

```text
      __________________
    /                  \
   |                    |
    \__________________/
```

ה-legs יכולים להיות מעט מעוקלים בפועל עקב רוח, נהיגה ורעש; אין לדרוש straight-line מושלם.

## 5. Figure-8

Figure-8 הוא SO דמוי Hippodrome שבו שני ה-legs מצטלבים. זהו self-crossing אמיתי של ה-centerline.

```text
       ______       ______
     /      \     /      \
    /        \   /        \
    \         \ /         /
     \         X         /
      \       / \       /
       \_____/   \_____/
```

דגשים מחייבים:

- ה-legs אינם חייבים להיות ישרים; מותרת עקמומיות רכה.
- נקודת החצייה יכולה להופיע בשתי פאזות שונות ולכן phase projection בעתיד חייב להשתמש גם בכיוון/מהירות כאשר המיקום לבדו אמביוולנטי.
- מבחינת תבניות סנכרון Figure-8 מנורמל לסמנטיקת Single-SO; `display/topology` נפרדים מהחוק הסינכרוני.

## 6. Double Hippodrome

Double Hippodrome מורכב משני Hippodromes שמחוברים דרך אותו מעגל פנייה: מרכז מעגל הפנייה המשותף זהה בשני ה-Hippodromes.

הנתיב הנוסע בפועל הוא **הגבול החיצוני של איחוד שני השטחים הפנימיים של ההיפודרומים**.

כתוצאה מכך:

- אין U-turn פנימי באזור החיבור.
- אין מעבר דרך נקודת connection עם היפוך heading כדרישה.
- המעבר מה-Hippodrome הראשון לשני רציף וחלק.
- שתי הישויות חולקות `shared turn-circle center`.
- period של Double הוא period של כל המחזור סביב הגבול המאוחד, ובקירוב יכול להיות כפול ממחזור Single מקביל.
- זווית הפתיחה בין שני ה-Hippodromes היא פרמטר גאומטרי רציף. **אין מגבלת מוצר או detector קשיחה של 10°–40°.**
- הטווח 10°–40° הוא **טווח QA מועדף בלבד** משום שזהו טווח תרחישים שהמערכת צפויה לפגוש לעיתים קרובות. הסימולטור ומערך הבדיקות יריצו צפיפות גבוהה של דוגמאות בטווח זה, וכן דוגמאות מחוץ לו כדי למנוע overfitting של האלגוריתם לטווח הבדיקות.
- אסור למסווג להשתמש בזווית 10°–40° כ-gate, penalty או prior שמונע זיהוי של Double חוקי מחוץ לטווח.

סכמה:

```text
      ________             ________
    /          \         /          \
   /            \_______/            \
   \                                 /
    \_______________________________/
```

מימוש הסימולטור בונה שני capsule areas בעלי אותו turn-center ומחלץ את exterior boundary של ה-union. הקשתות הפנימיות אינן חלק מהנתיב.

## 7. Double Figure-8

`DOUBLE_FIGURE_EIGHT` קיים בשם בלבד אך **אינו מוגדר גאומטרית עדיין**. אסור לממש detector או simulator עבורו עד לקבלת הגדרה מפורשת מהמשתמש.

## 8. מודל מבנה נתונים לסנכרון SO

שכבת הגאומטריה מופרדת משכבת תבנית הסנכרון.

מבנה התבנית המאושר:

```text
SO Template
  -> Route Instances
      -> routeKind: Single | Double
      -> geometry/profile reference
      -> Vehicle Slots
          -> vehicle type
          -> Quarter: Q0 | Q1 | Q2 | Q3
```

היחס בין רכבים נגזר מהרבעים ואינו נשמר כפרמטר כפול:

- הפרש 0 רבעים -> Same.
- הפרש 2 -> Opposite.
- הפרש 1 או 3 -> Mixed.

Figure-8 אינו יוצר חוק סנכרון חדש; הוא נשאר Single-SO מבחינת הסמנטיקה.

## 9. תרחישי סימולטור מחייבים

כל תרחיש מסווג כל דגימה ל-Ground Truth segment:

- `approach` — הדרך אל הנתיב לפני הכניסה למחזור.
- `route` — הדגימות שבוצעו על הנתיב המחזורי.
- `exit` — הדרך לאחר היציאה מהנתיב.

הסימולטור חייב להיות seed-deterministic ולתמוך לפחות בפרמטרים הבאים:

- sample interval משתנה, לרבות 1/2/5 שניות.
- period ומשך תצפית במספר מחזורים.
- rotation, scale ווריאציות גאומטריות חוקיות.
- GPS Gaussian noise.
- GPS spikes נדירים.
- רוח משתנה בזמן גם בעוצמה וגם בכיוון.
- packet/sample loss בסיסי.
- turn-dependent communication loss.
- contiguous outages בתוך פניות.
- approach ו-exit לפני/אחרי המסלול.
- ל-Double Hippodrome: sweep צפוף של זוויות פתיחה 10°–40° (למשל 10/15/20/25/30/35/40) וכן דוגמאות edge מחוץ לטווח. רשימת ה-sweep היא כיסוי בדיקה בלבד, לא חוק גאומטרי.

## 10. חוסר תקשורת בפניות — דרישת חובה

בפועל כלי רכב עשויים להתנתק מהרשת דווקא בזמן פנייה. לכן הסימולטור חייב לייצר תרחישים שבהם:

- שתי הישורות של Hippodrome נצפות היטב.
- חלק גדול או כל אזור הפנייה ביניהן חסר.
- לעיתים שתי הפניות חסרות כמעט לחלוטין, כך שהשרת רואה בפועל שני ענני נקודות דמויי קווים עם חור ביניהם.

היעדר הדגימות אינו evidence לכך שאין פנייה. המסווג העתידי יצטרך להשתמש ברציפות בזמן, בכיוון, במבנה הכולל וב-evidence ממחזורים אחרים; אסור לו לדרוש שנקודת הפנייה עצמה נצפתה בכל מחזור.

אין להמציא דגימות בתוך החור. מגבלת האינטרפולציה הכללית של המוצר נשארת 5 שניות; חור ארוך יותר נשמר כחוסר מידע.

## 11. מודל רוח בסימולטור

מטרת שכבת הרוח היא בדיקת robustness של הזיהוי, לא סימולציית דינמיקת רכב מלאה.

- נוצר וקטור רוח דו-ממדי שמשתנה באופן חלק בזמן.
- גם המגניטודה וגם הכיוון משתנים.
- ההשפעה על העקבה נשלטת באמצעות gain מפורש של הסימולטור.
- יש לשמור את וקטור הרוח Ground Truth בכל timestamp כדי לאפשר ניתוח מאוחר.
- אין להשתמש בפרמטרי הרוח כהנחה של המסווג; הם קיימים רק ליצירת perturbations.

## 12. כלל פיתוח והתאמה למפרט

- אין להוסיף RouteSubtype, topology, תכונת מעבר, dependency אלגוריתמי או כלל סנכרון על בסיס השערה.
- אם המסמך אינו מגדיר פרט שנדרש למימוש — יש לעצור ולבקש הבהרה מהמשתמש לפני כתיבת קוד.
- כל detector/simulator חדש חייב לכלול test שמפנה במפורש לסעיף המפרט שאותו הוא מממש.
- פרמטר של בנק תרחישים או sweep אינו הופך אוטומטית ל-constraint של המוצר.
- שינוי קוד גאומטרי מחייב בדיקת conformance מול מסמך זה לפני merge.
