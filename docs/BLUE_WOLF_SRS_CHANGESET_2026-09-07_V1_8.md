# Blue Wolf — SRS Amendment v1.8

**Date:** 2026-09-07  
**Status:** Normative functional and runtime amendment.  
**Applies together with:** the current official SRS chain and the v1.7 canonical architecture.

## 1. Purpose
This amendment records the accepted behavior added during the current development cycle. It does not replace the v1.7 canonical architecture; it makes the Figure-8 route definition, stateful Live processing, checkpoint isolation and navigation-truth rules explicit and testable.

## 2. Figure-8 route definition

### 2.1 Family and topology
A Figure-8 is an **SO route**. It is not a new synchronization family.

A Figure-8 SHALL be modelled as **one normal hippodrome whose two straight legs are crossed**:
- the two outer end turns remain ordinary outward hippodrome semicircles;
- the upper connection of one end is connected to the lower connection of the opposite end;
- the second straight leg performs the complementary crossed connection;
- the two straight legs intersect once inside the route;
- the route is one continuous closed cycle and one route entity.

A generic Lissajous/infinity-symbol approximation SHALL NOT be treated as the normative Figure-8 geometry when a parametric Figure-8 is generated by Blue Wolf.

### 2.2 Period and phase
A Figure-8 SHALL use one normal SO period, equivalent in cycle semantics to a single hippodrome. It SHALL NOT receive the doubled-period semantics of a Double SO route merely because the path contains two lobes.

Progress/phase SHALL be normalized arc length along the complete self-crossing closed trace. At the central crossing, geometric distance alone is insufficient to identify the active branch. The Core SHALL use motion/tangent evidence to preserve the physical leg being traversed and prevent phase jumps to the other crossing branch.

### 2.3 Grouping
For inter-route SO grouping, a Figure-8 SHALL use the same external grouping law as a single hippodrome:
- same external end-turn/axis interpretation;
- same compatible period semantics;
- same geometric proximity/orientation thresholds.

The internal crossing SHALL NOT make the route behave as a Double entity for grouping.

The public route evidence SHALL expose:
- `kind = "figure8"`;
- `crossedLegs = true` when a recognized parametric/geometric descriptor is available.

### 2.4 Scoring
Figure-8 scoring SHALL use the normal SO scoring components and configured weights. No dedicated hard-coded Figure-8 score multiplier is introduced. Route adherence SHALL be measured against the self-crossing canonical trace and synchronization SHALL use the configured SO template/phase relation.

## 3. SO Template Builder
The count-first SO Template Builder SHALL support three explicit entity counts:
- Single hippodrome;
- Double SO route;
- Figure-8.

Figure-8 SHALL:
- appear as a distinct selectable entity in layout generation;
- participate in mirror/symmetry de-duplication as a distinct symbol;
- use two placement halves, like a Single hippodrome;
- use the Single external neighbor-relation semantics;
- be previewed as a crossed-leg hippodrome;
- persist its count in `figure8Counts`;
- persist `figure8` in the SO `chain` and entity list.

Existing two-argument layout generation calls remain backward compatible by treating Figure-8 count as zero.

## 4. Simulator and independent GT coverage
The deterministic simulator SHALL contain executable Figure-8 navigation coverage. Figure-8 GT SHALL remain independent of production analysis.

At least one normal simulator scenario SHALL include a vehicle whose GT route kind is `figure8`. The production validation path is:

`Simulator scenario -> Raw NAV -> production Python Core -> result -> independent GT comparison`

The system test SHALL verify that the Core identifies the route as `figure8` and, where a geometry descriptor is returned, exposes `crossedLegs=true`.

A Figure-8 that is geometrically outside the configured SO grouping thresholds SHALL remain outside that SO group even though Figure-8 is a valid SO route.

## 5. Stateful Live analysis

### 5.1 Warm-up
An Operator live session SHALL warm the canonical Python Core once from the currently selected navigation window.

The first warm-up response SHALL prioritize current operational analysis. It SHALL NOT block the first usable Operator result on a full historical timeline reconstruction. The live session MAY begin with one current history frame and grow the bounded Timeline through subsequent incremental batches.

### 5.2 Five-second increments
After warm-up, each live poll SHALL send only navigation samples newer than the previously processed frontier. The normal active-source cadence remains five seconds unless changed by configured source settings.

A five-second Batch contains the individual samples/time points; it is not an averaged five-second measurement.

Overlapping source queries SHALL be de-duplicated by timestamp/vehicle identity before advancing Core state.

### 5.3 Shared Operator result
The Operator Analysis and Timeline/History views SHALL share the same stateful live Core session/result for the same source, server, window and configuration. Concurrent requests for the same cutoff SHALL not cause the same NAV delta to be processed twice.

Historical Investigation and short deterministic E2E fixtures MAY continue to use a fresh stateless current-Core replay where stateful live continuation is not the requested mode.

## 6. Operational checkpoint rules

### 6.1 Content
A checkpoint SHALL contain compact Python CoreSession state only. It SHALL NOT become a Raw NAV archive or duplicate Influx history.

### 6.2 Cadence
For real Influx Live operation, the primary Operator live session SHALL persist a checkpoint approximately every five minutes.

### 6.3 Recovery
On restart/recreation, a compatible checkpoint MAY be restored only when its processed frontier is covered by the newly queried navigation recovery window.

Recovery SHALL perform the following logical sequence:
1. restore compact Core state;
2. hydrate the pre-frontier route-fitting history from authoritative NAV;
3. feed only samples after the checkpoint frontier through normal `process_batch` processing;
4. catch up to the current requested cutoff;
5. continue with normal five-second Live batches.

Checkpoint/replay behavior SHALL be deterministic with uninterrupted processing at the same cutoff, subject only to insignificant floating representation differences that do not change route/group/score semantics.

### 6.4 Preview isolation
Template-preview analysis is non-operational. A preview-only Core session SHALL NOT:
- restore the primary operational checkpoint;
- persist or overwrite the primary operational checkpoint.

A live key becomes checkpoint-authoritative only through the primary Operator Analysis + History/Timeline flow (or an equivalent explicit primary-live role). Temporary configuration previews remain isolated.

## 7. Navigation truth and missing altitude
Missing source data SHALL remain missing.

In particular, an absent Influx altitude value SHALL be represented as `null`/missing in the normalized navigation contract. Blue Wolf SHALL NOT fabricate `altitude = 0` merely to satisfy a numeric type.

Altitude is not currently a direct scoring input, but its truth semantics SHALL still follow the single-navigation-truth rule.

## 8. Core replacement boundary
The Figure-8 and Live-session additions do not change the architectural replacement principle:
- UI does not contain a production algorithm fallback;
- DB does not contain the algorithm implementation;
- Influx access remains outside Core;
- Core accepts normalized NAV + immutable configuration/state contract;
- a future Core may replace Python without changing UI/DB when the public contract remains compatible.

The canonical current implementation remains Python until an explicitly accepted replacement passes the independent Core gate.

## 9. Required tests
A release containing this amendment SHALL include automated evidence for at least:
- crossed-leg Figure-8 topology recognition;
- Figure-8 active application-envelope output;
- Figure-8 external grouping compatibility with Single semantics;
- Figure-8 Simulator -> NAV -> Python Core -> GT validation;
- Figure-8 Template Builder layout persistence;
- warm-up followed by five-second incremental batches;
- fast current-analysis warm-up followed by Timeline growth from later live batches;
- duplicate/overlapping Live query suppression;
- uninterrupted vs checkpoint/restore/replay equivalence;
- checkpoint containing no permanent NAV history;
- preview sessions not becoming checkpoint-authoritative;
- missing Influx altitude remaining null;
- deterministic repeated simulator retrieval for the same explicit historical range;
- valid SI largest-compatible-component retention in the presence of a remote circle-like outlier;
- full integrated TypeScript/build/JS/browser release gate before public preview.

## 10. Release truth
No Figure-8, Live-session, checkpoint or data-quality capability is considered implemented merely because a UI label or mock says so. PASS requires executable production-path evidence. A public preview SHALL not be declared verified until the exact release commit passes the integrated release workflow and the public authenticated URL is checked.

## 11. Deterministic simulator history boundary
For simulator history, determinism applies to the complete retrieval contract, not only to the mathematical route generator.

For an identical explicit request tuple `(serverId, from, to, grouping configuration, wind mode, target sampling policy)`, repeated calls SHALL produce the same effective range, sample timestamps, samples and provenance regardless of the wall-clock milliseconds at which the function is invoked.

The rolling 30-day availability rule SHALL therefore use a stable reference derived from the explicit request when the request itself provides the historical cutoff. An internal fresh `now()` value SHALL NOT shift the lower bound between two otherwise identical historical requests.

If a requested range is clipped by the 30-day availability boundary, that clipping SHALL be deterministic for the same explicit request.

## 12. Robust SI grouping
SI grouping SHALL be based on a compatible component of route evidence, not on an all-or-nothing requirement across every track temporarily classified as circular.

The Core SHALL:
- evaluate circle-track compatibility using the SI geometric law, including compatible centres and rotation/direction;
- select the largest mutually connected compatible SI component;
- require at least two members before exposing an active SI group;
- keep remote/incompatible circle-like tracks outside that group;
- prevent one remote or transiently misclassified circular outlier from erasing an otherwise valid SI group.

A deterministic regression fixture containing a valid three-vehicle SI formation plus a remote circular outlier SHALL remain part of the independent Core suite.

## 13. Python Core transport behavior
The application/Core transport is an infrastructure boundary only; it SHALL NOT change algorithm semantics.

The HTTP service SHALL support persistent HTTP/1.1 request handling suitable for repeated live batches. Successful Core responses SHALL be flushed as complete JSON responses. Structured Core validation failures SHALL preserve their meaningful HTTP error status through the web proxy, while an actual inability to reach the Python service may be represented as a service-unavailable transport failure.

Transport failure SHALL never trigger a hidden TypeScript algorithm fallback or simulator substitution.
